## TL;DR

- GitHub のスタック PR(2026-07-30 パブリックプレビュー)を、個人の private リポジトリで **3 層**組んで実測した
- 一番知りたかったのは **squash マージしたら履歴が崩れるのか**だった。**崩れなかった**
- 下層を squash マージした瞬間、**サーバー側で上層の PR のベースが自動的に main へ切り替わる**。squash で失われた線形性は `gh stack sync` が「adjusted for merged PR」でスカッシュコミットの上へ載せ替えて復元する
- 射程は明確に狭い。**同一リポジトリ限定**(クロスフォークも不可)/ **直列チェーンのみ**(DAG は表現できない)/ 全ブランチ間の **linear history がマージの厳格要件**
- **サーバー側リベースで conflict した時の挙動は未検証**。公式ドキュメントにも記載を見つけられなかった

---

## リリースの動機は、公式がほぼ言い切っている

この機能が「大きな変更を依存関係のある小 PR の連鎖として出せるようにするもの」だという説明は、どこを読んでも同じだった。気になったのは、なぜ今なのかのほうだ。

発表と同じ日、GitHub の Cassidy Williams が公式ブログでこう書いている。エージェンティックな開発では自分でコードを書かなくていいせいでスコープクリープが起きやすく、1 万行の PR を作りたくなる、と。

同じ日に、Copilot アプリ側にも「スタックセッション」が入った。エージェントが PR を作ったあと、そのブランチから次のセッションを自動で積んで、依存する PR を出していく仕組みだ。

つまりこれは、**エージェントの出力を受け止める側の整備**とセットで出ている。プラットフォームが「巨大な 1 本」ではなく「依存し合う小さい多数」を選ばせにきた、という読み方が自然だと思う。

## 僕が知りたかったのは、squash 運用でも成立するかだった

スタック PR 自体は新しい発想ではない。大きな会社の内部や Graphite のようなツールで、前からあるやり方だった。公式化されたことのほうがニュースだ。

それでも手を出さずにいた理由が、僕にはひとつあった。**squash マージだ。**

下から順に積んだ PR の一番下を squash でマージすると、そのブランチのコミットは 1 個の新しいコミットに潰れる。潰れた時点で、上に積んである層が参照しているコミットは、もう main の履歴のどこにもない。**履歴の足元が抜ける。**手でリベースし直すことになるなら、依存の管理を GitHub に任せた意味が薄い。

そこを確かめたくて、実際に組んだ。

## 3 層で組んだ

private リポジトリを 1 つ用意して、こういう 3 層にした。

1. 小さなユーティリティ関数を足す
2. その関数を使う機能を足す
3. その機能のドキュメントを足す

意図的に、下から順に依存させている。2 は 1 がないと動かないし、3 は 2 がないと嘘の説明になる。

手順そのものは短い。

```bash
gh stack init
gh stack add -Am "add util"      # ステージ + コミット + 次のブランチ作成が 1 発
gh stack add -Am "use util"
gh stack add -Am "add docs"
gh stack submit                  # push + PR 群をまとめて作成
```

`submit` で PR が 3 本立った。ターゲットは 1 本目が main、2 本目が 1 本目のブランチ、3 本目が 2 本目のブランチ。狙った通りの連鎖になっている。

### 先に踏んだ小さいところ

2 つある。ひとつ、`gh` が 2.73 のままだと動かない(2.90.0 以上が要る)。2.96.0 に上げた。もうひとつ、**`submit` は draft で PR を作る。**マージしたければ `gh pr ready` が別に要る。最初、なぜマージボタンが出ないのか分からず数分探した。

### 下層を直したときの伝播

本題の前に、こちらを確かめた。1 層目に追加のコミットを入れて `gh stack rebase` を打つと、上の 2 本に伝播する。そのあと `submit` が force-push と PR の更新まで面倒を見る。**手作業はゼロだった。**

ここまでは想像どおりだ。問題は次だった。

## squash マージした瞬間に、上層のベースが勝手に切り替わった

1 層目だけを squash でマージした。

マージした瞬間、**2 層目の PR のベースが、サーバー側で自動的に main へ切り替わった。**こちらは何も打っていない。GitHub がスタックを認識しているので、下が消えたら次の層のターゲットを繰り上げる、という処理が向こう側で走っている。

ただ、この時点では履歴は線形ではない。2 層目のブランチが載っているコミットは、squash で潰される前の古いコミットのままだからだ。

そこで `gh stack sync` を打った。出力にこう出る。

```
adjusted for merged PR
```

**2 層目が、squash で生まれた新しいコミットの上に載せ替わった。**main → squash コミット → 2 層目、という線形の履歴に戻っている。

つまり、僕が心配していた「squash で足元が抜ける」は、**プラットフォーム側の自動リターゲットと、CLI の sync の 2 つで塞がれている**。squash 運用のままスタックを使える。ここが今回いちばん確かめたかったところだった。

## 射程は狭い。狭いことが分かっているのは良いことでもある

一方で、できないことがはっきりしている。

- **同一リポジトリ限定。**クロスフォークも不可だ。API のリポジトリとクライアントのリポジトリをまたぐ依存は、従来どおり PR のリンクとマージ順の運用で管理するしかない
- **直列チェーンのみ。**「C が、独立した A と B の両方に依存する」という形は表現できない。直列に並べて順序を強制するか、別のスタックに分けるかになる
- **スタック内の全ブランチ間で linear history がマージの厳格要件。**マージコミットを挟むと成立しない
- GitHub Desktop は未対応。API 経由でマージを自動化している場合は、新しいスタック用のマージ API への移行を点検する必要がある

3 番目が地味に効く。エージェントに委譲するとき、**マージコミットを作らせない規律が前提**になる。自由にやらせると壊れる場所がひとつ増えた、ということでもある。

## 未検証: conflict したときに何が起きるか

正直に書いておく。**サーバー側のリベースで conflict が起きたときの挙動を、僕は確かめていない。**公式ドキュメントにも記載を見つけられなかった。

今回の実測は、conflict しない素直なケースだけを通している。実運用で怖いのはそこではなく、3 層目まで積んだあとに 1 層目のレビューで大きく方向が変わる場面のほうだ。そこは次に確かめる。

## この機能が噛み合う場所

別件で、AI エージェント 9 体に並列で作業させて、PR が 44 本立った日があった。そこで分かったのは、**1 依頼 1 成果物に割ると委譲そのものは回る**ということだった。1 つの依頼に成果物を 2 つ以上入れると止まる。割れば動く。

ただ、割ったぶんだけ依存が生まれる。A の上に B、B の上に C。そのリベースを手で回していたのは僕だった。**委譲した先の作業量は減るのに、統括側のコストが増える。**割り方の問題ではなく、割った結果を並べる場所がなかった、という構造だ。

今回のスタック PR は、ちょうどそこに刺さっている。プラットフォーム側から出てきた回答が、自分が手で埋めていた穴と同じ形をしていた。**同じ問題を、向こうも見ていた**ということだと思う。

## まだ賭けの段階だ

とはいえ、これが標準になると言い切るには早い。反対側の目もある。

スタックは**書き手に規律を要求する。**小さく割る、マージコミットを作らない、順番を守る。エージェントにその規律を課すコストが、受け皿としての便益を上回るなら、実務は「巨大な PR を出して、レビュー側の AI で受ける」ほうに倒れる可能性がある。レビュー側の AI が伸びるほど、スタック不要論の燃料になる。

だから負ける条件を先に書いておく。**2026 年 10 月末の時点で、自分の実運用に一度もスタックを投入していなくて、かつ GitHub がこの機能を先へ進めていなかったら、この見立ては死ぬ。**そのときは、素直にそう書く。

squash 運用でも崩れないことは、今日確かめた。使うかどうかは、これからだ。
