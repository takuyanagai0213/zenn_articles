## TL;DR

- AI エージェントに仕事を投げて止まるとき、原因は能力でなく**タスクの形**であることが多い
- 完了条件を**エージェント自身がコマンドで真偽を判定できる形**にすると通る
- 実測: 同じ依頼が **85 分で成果物ゼロ → 6 分で完了**に変わった
- ただし「0 件」を条件にするときは**対照とセットで書く**。0 になる理由が 2 つあると何も測っていない

## 85 分ゼロが 6 分になった

設定画面の改善をエージェントに投げた。こう書いた。

```
①カード化 ②インラインスタイル剥がし ③配色統一
```

**85 分経って、成果物はゼロだった。**

1 件に絞り、完了条件をこう書き直した。

```
apps/web/app/settings/ 配下で grep 'style={{' が 0 件になること
```

**6 分で完了した。**

差は能力ではない。**何をもって終わりとするかが、機械で判定できる形になったかどうか**だけである。

## 「改善して」はなぜ止まるのか

エージェントは作業を進めながら「これで終わりか」を自分に問う。このとき

```
デザインを改善する   → 終わりが判定できない。無限に続けられる
grep が 0 件         → 打てば分かる
```

**終わりが判定できない依頼は、完走しない。**人間なら「まあこのへんで」と切り上げるところを、エージェントは切り上げる根拠を持てない。止まるか、延々と直し続けるかになる。

## 書き換えの型

実際に使っている対応表をそのまま出す。

| 悪い完了条件 | 良い完了条件 |
|---|---|
| デザインを改善する | `grep 'style={{'` が **0 件** |
| セキュリティを固める | `curl --path-as-is '.../../etc/passwd'` が **404** |
| テストを充実させる | **変異注入で N 箇所を壊し、それぞれテストが落ちること** |
| 動くようにする | **設定を書かずにブラウザで開き、イベントが 202 で届くこと** |

### 3 行目が一番効く

**「テストが通ること」を完了条件にしてはいけない。**テストを書き換えれば通ってしまうので、直った証拠にならない。

代わりに**変異注入**を使う。守りたい挙動をわざと壊して、**テストが落ちることを見る**。落ちなければ、そのテストは最初から何も測っていない。

```bash
# 守っているはずの箇所を壊す
sed -i '' 's/if (!isAuthorized)/if (false)/' src/auth.ts
npm test          # ← ここで赤くならなければ、そのテストは無意味
git checkout src/auth.ts
```

⚠️ **変異を当てる前に、まず緑であることを確かめる。**赤い状態から当てると、変異が効いたのか元から赤いのか区別できない。手順は **緑を見る → 壊す → 赤を見る → 戻す → 緑を見る** の 5 段。

## 「0 件」の落とし穴 ── 対照をセットで書く

上の表の 1 行目が成立しているのは、**`style={{` が 0 件になる理由が 1 つしか無い**からである。

**理由が 2 つ以上ある文字列を選ぶと、その条件は何も測らない。**

実際にやってしまった例がある。API に送るフィールド名をキャメルケースからスネークケースへ
揃える依頼で、こう書いた。

```
grep -rn "<旧フィールド名>" が 0 件
```

**満たせるはずのない条件だった。**その名前は、**置き換えたい箇所以外に 5 つの正当な用途があった。**

- ORM の列プロパティ定義
- 関数の引数名
- URL の組み立て
- SQL の列別名
- 画面側の内部状態のキー

**置き換えたいのは「API に送る 1 箇所」だけなのに、grep は 6 箇所全部を拾う。**
そして**文字列としては区別が付かない。**

### したがって

**0 件を条件にするなら、必ず対照を添える。**

```
grep X が 0 件、かつ grep Y が 1 件以上
```

`Y` は**必ず当たるはずのもの**。当たらなければ、その検査は環境ごと壊れている（パスが違う、ディレクトリを間違えている、grep のオプションが効いていない）。

そして**書く前に 1 度問う** ── **「この 0 件は、何通りの理由で 0 になりうるか」**。2 つ以上あるなら条件にしない。

### 文字列で区別が付かないときは、外へ出るものを見る

ソースの grep は、同じ綴りの別用途を巻き込む。**実際に外へ出るもの**を見るほうが確実である。

- 送信された HTTP リクエストの本文を `JSON.parse` して確かめる
- 生成された成果物そのものを検査する
- 実行時の出力を見る

上の例では最終的に「変異を 4 方向に当てて全部赤くなること + 送信本文をパースして確かめるテスト」に差し替えた。**そちらのほうが、直したいことの直接の証拠になっている。**

## grep -c で数えない

ついでに 1 つ。**件数を数えるときに `grep -c` を使わない。**

```bash
grep -c 'class="jump"' toc.html     # → 1   ⚠️ 実際は 8 個ある
grep -o 'class="jump"' toc.html | wc -l   # → 8
```

`-c` が数えるのは**行数**である。1 行に複数あると壊れる（minify された JS、1 行の HTML、JSON）。

**`-c` が安全なのは「0 か、0 でないか」を見るときだけ。**「N 件あるはず」の検算には `-o | wc -l` を使う。

## まとめ

依頼を書き終えたら、3 つ確かめる。

1. **完了条件は、コマンドを打てば真偽が分かる形になっているか**
2. **「0 件」を使っているなら、対照（必ず当たるもの）を添えたか**
3. **「テストが通ること」を条件にしていないか**（変異注入に置き換える）

これだけで、止まる依頼はかなり減る。
