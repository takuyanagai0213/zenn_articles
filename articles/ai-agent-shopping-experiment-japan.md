# dots に自分の店で 3 回買い物をさせたら、エージェントは署名つきで名乗ってきた

## はじめに

2026 年 10 月、日本からも個人向けの AI エージェントが使えるようになってきた。OpenAI の dots、xAI の Grok Bot、Meta の Muse。Anthropic の Claude Duet はまだ米国だけだ。

どれも「人の代わりにブラウザを操作して、調べて、買う」エージェントだ。

僕は普段、アフィリエイト広告の計測の仕事をしている。だから一番気になったのはこれだった。**エージェントが買い物をしたとき、売る側にはそれがどう見えるのか。そして「誰の紹介で売れたか」は残るのか。**

調べても日本語の記事は見つからなかった。なので自分で店を作って、dots に 3 回買わせてみた。

## やったこと

- Cloudflare Workers で、100 円のデジタル商品を 1 つだけ売るページを作った
- 決済は Stripe の支払いリンク(テスト環境。お金は動かない)
- ページへのアクセスは全部、D1 に記録した(IP、User-Agent、Referer、署名系のヘッダ、ASN など)
- 比べるために、先に人(僕)が 1 回買った

dots への頼み方は 3 通り。

1. 売り場の URL を直接渡して「買って」
2. 偽の比較記事を渡して「記事でおすすめされている商品を買って」(記事 → 紹介リンク → 売り場)
3. 売り場の URL とクーポンコードを渡して「インフルエンサーが教えてくれたコードで買って」

## 発見 1: dots は普通の Chrome に見えるが、署名で名乗る

人と dots で、売り場に届いたリクエストを並べるとこうなる。

| | 人 | dots |
|---|---|---|
| User-Agent | Mac の Chrome | Linux の Chrome(名乗らない) |
| IP の持ち主 | 自宅の回線 | ASN 13335、組織名の表示は OpenAI |
| Accept-Language | ja, en-US, en | ja-JP のみ |
| Signature-Agent | なし | `"https://chatgpt.com"` |
| Signature-Input | なし | ed25519、`tag="web-bot-auth"` |

User-Agent だけを見ると、dots は普通の Chrome と区別がつかない。でも、すべてのリクエストに **Web Bot Auth** の署名が付いていた。Signature-Agent は `https://chatgpt.com`。署名は OpenAI の鍵で検証できるので、なりすましでないことまで確かめられる。

つまり、サイト運営者は「エージェントの来訪」を User-Agent ではなく署名で数えられる。

ついでに、この記事の元になったメモを公開したら、X に告知するより先に Exa のクローラーが `Signature-Agent: "https://crawler.exa.ai"` を付けて来た。署名で名乗るエージェントは、少なくとも 2 つ見つかった。

## 発見 2: 紹介リンクを踏めば、紹介元の ID は購入まで残る

2 回目は、アフィリエイトの仕組みを小さく再現した。

- 比較記事に紹介リンク `/go?aff=media-ramen-001` を置く
- 紹介リンクは Cookie に紹介元を入れて、売り場へ 302 で飛ばす
- 売り場は紹介元を Stripe の支払いリンクに `client_reference_id` として付ける

dots は記事を読み、紹介リンクを踏み、売り場から Stripe に進んで買った。かかったのは 53 秒。**紹介元の ID は、Cookie にも URL のパラメータにも、購入後のページまで残っていた。**dots 自身も「決済画面の URL に紹介識別子が付いていた」と報告してきた。

エージェントが媒体のリンクを通る限り、今のアフィリエイトの計測はそのまま動く。

逆に言うと、**エージェントが媒体を読むだけで、売り場へ直接買いに行ったら、紹介元は付かない。**1 回目(URL を直接渡した回)がまさにそれで、記録の紹介元の欄は空だった。媒体の記事が購入の判断に効いていても、成果の線には載らない。SEO で稼いできた媒体にとっては、ここが一番厳しいところだと思う。

## 発見 3: エージェントのブラウザは、前の Cookie を持ち越す

3 回目はクーポンの実験だった。記事を通さず、売り場の URL とコードだけを渡した。

dots はコードを入れて、100 円が 90 円になった。経路が直接でも、コードがあればインフルエンサーの紹介だと言える。

ところが、記録を見ると紹介元の Cookie(記事の `media-ramen-001`)が付いていた。2 回目に入った Cookie を、dots のブラウザが持ち越していたのだ。IP は前回と違うのに、Cookie は同じだった。dots のブラウザは、人のブラウザと同じように利用者ごとに状態を持ち続けている。

結果として、1 回の購入に紹介元が 2 つ付いた。Cookie は「記事」、コードは「インフルエンサー」。最後のクリックの Cookie で決める今の仕組みだと、この成果は記事のものになる。人の世界でもある「二重の紹介元」が、エージェントでも同じように起きる。

## おまけ: 決済のときの IP は、売り場で見た IP と違う

Stripe のダッシュボードで dots の決済を見ると、記録された IP は、売り場が見た IP(Cloudflare 経由の OpenAI)とは別のものだった。IP で来訪と決済を結ぶ計測は、エージェントでは崩れる。決済 ID か紹介元の ID で結ぶ必要がある。

## まとめ

- dots は User-Agent では普通の Chrome だが、Web Bot Auth の署名で名乗る。来訪は署名で数えられる
- 媒体の紹介リンクを通れば、紹介元の ID は購入まで残る。今の計測はそのまま動く
- 媒体を読むだけで直接買いに行かれると、紹介元は消える
- エージェントのブラウザは Cookie を持ち越すので、クーポンと Cookie の紹介元が重なることがある
- 売り場と決済で見える IP は違う

エージェントの買い物は、計測の側から見ると思っていたより人に近かった。差が出るのは仕組みではなく、エージェントが何を読んで、どの経路で来るかだ。

## 確かめていないこと

- Stripe の注文データに `client_reference_id` とコードが残ったかの API 確認
- Grok Bot や Muse が Web Bot Auth の署名を付けるか
- 本物の決済(本物のカードや Link のエージェント向けウォレット)での挙動
- dots で試したのは各 1 回だけ。回によって違う動きをする可能性はある

続きを試したら、また書く。
