ルールというのは、エージェントが読むファイルのことです。編集しているファイルや会話の内容に応じて自動で読み込まれ、「こういうときはこうしろ」を伝えます。スキルが「呼び出す手順書」だとすれば、ルールは「呼ばなくても効いている制約」にあたります。

## 中身を見せる ── 抜粋 6 本

カタログだけだと「で、実際どう書いてあるのか」が分からないので、短くて効きの強いものを 6 つ出します。

### 1. 検査が通る理由は 1 つか、2 つ以上か(`verify.md` §11)

配信ディレクトリの外へ出られないことを、こう確かめていました。

```
curl '.../../package.json' が 404 であること
```

通っていました。ところがその後、同じディレクトリに `package.json` を新しく置きました。すると `..` は正規化で潰れて配信ディレクトリの直下を指し、そこに実在するようになったので **200 が返りました**。

404 だったのは「防御が効いていたから」ではなく「そこにファイルが無かったから」でした。判別の問いは 1 つになります。

> **「この検査が通る理由は 1 つか、2 つ以上あるか」**
> 理由が 2 つ以上ある検査は、いずれ弱いほうの理由だけで通るようになる。

だから検査対象を `/../../../etc/passwd` のような「配信対象に実在しえないもの」へ差し替えました。

### 2. 完了条件を機械で測れる形にする(`delegation-prompt.md` §5)

| 悪い完了条件 | 良い完了条件 |
|---|---|
| デザインを改善する | `grep 'style={{'` が **0 件** |
| セキュリティを固める | `curl --path-as-is '.../../etc/passwd'` が **404** |
| テストを充実させる | **変異注入で N 箇所を壊し、それぞれテストが落ちること** |
| 動くようにする | **設定を書かずにブラウザで開き、イベントが 202 で届くこと** |

最後の行が要点になります。「テストが通ること」を完了条件にすると、テストを書き換えれば通ってしまうので直った証拠になりません。**成果物の外側で観測できる事実**を条件に置きます。

このルールには続きがあって、書いた当日に 2 回自分で破ったことまで書いてあります。「今回は守った」と思っているときほど数えること、と。

### 3. 複数のリポジトリを跨ぐときに `cd` を使わない(`traps.md` §33)

```bash
# 危ない: 後半が別のリポジトリで走る
cd ~/repo-a && gh pr merge 77 && ... && git rm CLAUDE.md && cat > CLAUDE.md <<'EOF' ...
```

1 日に 3 回踏みました。2 回は誤判定で済みましたが、3 回目は資料側で実行するつもりの「`CLAUDE.md` を案内文へ差し替える」が実装側で走り、**正しいファイルを削除して別内容で上書きし、そのまま直接コミットしました。**push 前に気づいて戻しましたが、push していたら取り返せませんでした。

処方は 1 行です。**複数リポジトリを跨ぐ作業では `cd` を使わないことです。**`git -C <path>` と絶対パスを使います。`cd` を使うなら 1 呼び出し 1 リポジトリに限ります。

### 4. 空の出力を、事実の主張として読まない(`verify.md` §13)

1 セッションで 4 回踏みました。

- 1MB 超のファイルを探すコマンドが空 → 「1 つも無い」と読みました。**実際はエラーで途中終了していました**(2.6MB の画像がありました)
- 変異注入したら「テストが無い」 → 「その検査は存在しない」と読みました。**実際は自分の当て方がファイルを構文エラーにしていました**
- 未ログインの `curl` が 307 → 「その経路は無い」と読みました。**存在しない経路も 307 でした**
- `grep` が空 → 「その要素は無い」と読みました。**`grep` は行単位で、改行を挟んだ構造にはマッチしません**

処方のひとつが変異注入の手順になります。**緑を見る → 変異を当てる → 赤を見る → 戻す → 緑を見る**の 5 段です。赤い状態から変異を当てると、変異が効いたのか元から赤いのか区別できません。

### 5. 着手前に予想を取る(`approval.md` §0)

分類・分析・調査・レビューのように、出力が人間の判断材料になる作業を頼まれたとき、**着手前に「予想を 1〜3 行」もらうまで着手しない**というゲートです。

> この 802 件、分類する前に「自分はこう分かれるはずだ」を 1〜3 行ください。後で出力と突き合わせます

なぜ着手前でなければならないか。成果物が出てから予想を求めると、**認知負荷のピークで最もコストの高い行為を要求する**ことになり、確実に落ちます。実際そうやって失敗した記録が同じ節に書いてあります。

そして予想と出力が一致したときは「確認できた」ではなく**危険信号**として扱います。自分と同じ意見の AI を選択的に受け入れているだけかもしれないからです。一致した項目こそ抜き打ちに混ぜます。

### 6. 機械に触らせない 1 行を決める(`artifact-freshness.md`)

進捗ボードには 2 つの印を入れてあります。数字を差し替える範囲を囲う目印と、本文がどの時点のコードに対応しているかを示す `data-prose-sha` です。

> **`data-prose-sha` を書き換えるのは人だけ。**本文を直したセッションが、その時見ていた状態に書き換える。機械は絶対に触らない。触った瞬間に「本文を読んでいないのに最新だと言う」装置になる。

この設計のいいところは、**放置しても嘘にならない**ことです。人が本文を直さなければ、ボードは「本文は N 本ぶん遅れている」と自分で言い続けます。

## 書き足しの速度

ルールの中に出てくる日付を月別に数えると、こうなります。

| 月 | 日付の出現数 |
|---|---|
| 2026-03 | 7 |
| 2026-04 | 33 |
| 2026-05 | 59 |
| 2026-06 | 65 |
| 2026-07 | **133** |
| 2026-08(6 日時点) | 20 |

7 月だけ突出しています。日別に割ると **7/30 が 28 箇所、7/29 が 15 箇所**で、この 2 日だけで 43 になります。

何があったかというと、エージェントを 9 体並べて 15 時間走らせました。PR は 44 本出ました。そこで起きたことが `delegation-prompt.md` に 21 箇所、`verify.md` に 18 箇所、`traps.md` に 31 箇所ぶん書き足されました。

ここで観察できることが 2 つあります。

ひとつ。**ルールが増えたから事故が減ったのではなく、並列で走らせる量が増えたから事故が増えたんです。**加速しているのは学習曲線ではなく、扱っている量のほうです。

もうひとつ。**事故の種類が変わっています。**3 月から 4 月にかけての事故は自分の手癖でした ── 数を数え間違える、PR の説明を手で書く、通知を 1 件ずつ実況する。7 月の事故は構造のほうにあります ── 委譲した先が止まっていることに 2 時間 18 分気づかない、報告が 1 通ずつ遅れて届く、検査が何も測っていない。

**1 人で書いていた頃の事故と、9 体に任せている頃の事故は別物でした。**

## 効かなかったもの・消したもの・保留したもの

成功例だけ並べると、世にある設定集と同じになります。だから外した側も出します。

### 棚卸しをして、1 本も消せなかった

`strategy.md` には「モデル世代交代時の棚卸し」という手順が書いてあります。新しいモデルが出たら、細かすぎる手順指示を削り、「CRITICAL: You MUST」のような強調を弱め、強制的な足場を外します。公式のガイドが明示的にそう推奨しています。

2026-08-04 にそれをやりました。25 本すべてに「最終検証 / 検証ステップ / 念のため / 再確認 / 再検証」で検索をかけました。

**ヒットは 2 件、いずれも誤検出でした。削除は 0 件。**

理由ははっきりしていて、**事故から生まれたルールは最初から「機械で測る形」で書かれていた**からです。「念のためもう一度確認せよ」ではなく「`wc -l` で数え直す」「変異注入して落ちることを見る」と書いてあります。判定の一行はこうなりました。

> **「その検証は、コマンドの出力が根拠になるか?」**

ならない検証指示は書きません。逆に言えば、**削れる指示を書いていたら、それは最初から効いていなかったんです。**

### 同じ日の朝に書いた既定を、夜に反転した

`delegation-prompt.md` の §0 は「委譲するかを先に決める」という節で、2026-08-04 の朝に「既定は委譲しない」と書きました。公式ガイドが「新しいモデルは委譲しすぎるので抑えよ」と言っていたからです。

その日の夜に反転して「既定は委譲する」に書き換えました。理由は現場のほうにあって、CI が 6〜8 分かかる環境では、親が実装に沈むコストのほうが大きいんです。親が沈むとその間ほかの全部が止まります。

節の末尾にはこう書いてあります。**「既定を反転したのは起動判定を緩めたのであって、後始末を緩めたのではない。」**完了条件を機械で測る、現物で確認する、定期監視する、終わったら閉じる ── この 4 つは据え置きました。

### 義務化したものを、2 ヶ月後に廃止した

`traps.md` §17 に、廃止の記録が残っています。あるコマンドが権限設定で止められたとき、別経路で迂回することを 2026-05-12 に義務化しました。2 例の実績もありました。

2026-06-18 に廃止しました。理由は、**迂回路が存在すること自体が、設定した禁止を「形だけの禁止」にしていた**からです。本当に止めたいなら、その手前のプラットフォーム側で止めるべきでした。二重管理の認知負荷も乗っていました。

節には廃止した経緯だけが残っていて、手順は消えています。

### 「これは分かっていない」と書いてあるもの

`traps.md` §9 は、長時間の待ち受け処理をどう書くかの節です。バックグラウンド実行で書いたスクリプトが早期に止まる事象を複数回観察しましたが、**再現条件も原因も特定できていません。**

だから節にはこう書いてあります。「観察事実ベースの暫定的な指針であり、再現条件と原因が判明したら更新する」。分かっていないことを分かっていないと書いたまま、実用上動くほうの手段を既定にしてあります。

§20 はさらに弱くて、「N=1 の観察、2 回以上観察したら正式化する候補」と明記してあります。**昇格待ちの棚**が用意されています。

### 書いても発火しなかったもの

一番痛いのはこれです。

`approval.md` の §0 は、そもそも「型は既にあるのに発火しない」という実測から生まれています。「見る前に予想を立てる」は別のところに書いて運用していたのに、実際に検索してみたら **予想を書いたメモは 0 件**でした。だから「人間が心がける規律」から「エージェント側が止める構造」へ移しました。

`verify.md` §13 にも同じ形が出てきます。空の出力を事実として読むな、と節を書いた**翌日に同じことを踏んでいます。**節にはそのまま「型の在庫はあるのに発火しない」と書いてあります。

**書けば効くわけではないんです。**ルールに書くことで確実に変わるのは、エージェントが読むかどうかであって、人間が思い出すかどうかではありません。

### ルールをルールで測ると、記録が測定を汚す

これは笑い話に近いです。棚卸しのために 25 本を検索して「ヒット 2 件」という結果を得ました。その結果を同じ 25 本の中に書きました。

もう一度同じ検索をかけると **9 件返ってきます。**増えた 7 件は、監査の結果を記述した文そのものでした。

| 状態 | ヒット |
|---|---:|
| コミット済みの状態 | 1 |
| 監査を実施した時点 | 2 |
| 記録を書いた後 | 9 |

対処は 1 行で、**測定は作業ツリーではなくコミット済みの状態に対して行います**。そして測った数字を残すときは、いつ・どの状態を測ったかを併記します。

## これから作る人向けの順番

25 本を一度に作る必要はありません。**というより、作れません。**全部、事故が起きた後に書いたものだから、事故が起きていないルールは書きようがないんです。

自分の履歴を実際の順番で並べると、こうなっています。

| 順 | ルール | 最古の記録 |
|---|---|---|
| 1 | `record.md` | 2026-03-07 |
| 2 | `strategy.md` | 2026-03-15 |
| 3 | `pr-workflow.md` | 2026-03-16 |
| 4 | `linear.md` | 2026-03-23 |
| 5 | `verify.md` | 2026-03-24 |
| 6 | `accuracy.md` | 2026-04-03 |
| 7 | `traps.md` | 2026-04-21 |
| 8 | `spawn-preflight.md` | 2026-04-24 |
| 9〜12 | `deploy-declaration.md` / `spec.md` / `subagent-verification.md` / `recall.md` | 2026-04-25〜28 |
| 13〜19 | `quota.md` / `completion.md` / `approval.md` / `readability.md` / `delegation-prompt.md` / `elicitation.md` / `review-coverage.md` | 2026-06-28〜07-04 |
| 20〜25 | `draft.md` / `line-messaging-liff.md` / `schedule-proposal.md` / `crystallization-ritual.md` / `artifact-freshness.md` / `slack-formatting.md` | 2026-07-06〜30 |

この順番から、これから始める人向けに 5 段だけ抜き出します。

**1 本目は「数える」ルールです。**公開する直前に、数字を実際のコマンドで数え直します。記憶の値を使いません。これが一番早く効いて、一番よく壊れます。

**2 本目は「完了の定義」です。**テストを実行して、その出力を報告に含めるまでが完了です。「動くはず」で飛ばしません。

**3 本目は「罠の置き場」を 1 本作ります。**個別の罠ごとにファイルを分けません。1 本に番号を振って積んでいきます。自分の場合それが 946 行になりましたが、探すのは検索なので困っていません。

**4 本目は「出す前に止める」1 本です。**外に投稿する、共有環境に反映する、消す ── 戻せない操作の直前に 1 行宣言します。

**5 本目は委譲を始めてからです。**エージェントを 2 体以上並べるまでは要りません。並べた瞬間に、完了条件・監視・後始末が一気に必要になります。

そして最後にひとつ。**25 本を目指さないことです。**数を目標にすると、事故が起きていないのに書いたルールが混ざります。それは削れるルールであり、削れるルールは最初から効いていません。

## 負け条件

この記事の主張は「事故から書いたルールだから効いている」です。これが誤りだと分かる条件を書いておきます。

**2026-11-06 に、この記事に書いた事故と同じ型の事故が何回再発したかを数えます。**3 件以上再発していたら、この 25 本は装置ではなく記録でしかなかったことになります。

現時点で不利な材料はすでに 2 つあります。空の出力を誤読するなと書いた翌日にそれを踏んでいますし、予想を先に取れという型は検索したら運用実績 0 件でした。**書いた側の自分が、書いた翌日に発火していません。**

だから確認日を決めて、カレンダーに入れてあります。
